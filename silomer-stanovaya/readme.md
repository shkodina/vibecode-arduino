# silomer-stanovaya

Силомер для становой тяги на Lolin NodeMCU v3, HX711, OLED GM009605 и
S-образном тензодатчике YZC-516C 1t. Контроллер показывает текущий вес,
максимум текущего измерения и максимум прошлого измерения через OLED,
веб-страницу, JSON API и WebSocket.

## Идея и цель

Устройство включается от обычного 5-вольтового зарядного для телефона.
Переключатель выбирает режим сети. Дальше везде используются полные названия,
чтобы не путаться в сокращениях:

1. `UseExistedWiFi` - использовать существующую WiFi-сеть из `.env`/EEPROM;
2. `StandAlone` - поднять свою WiFi-сеть `lolinsilomer` с паролем
   `lolinsilomer`, без роутера.

Все быстрые числа для железа лежат в `config.h`: пины, порт HTTP, порт
WebSocket, период чтения веса, заводской триггер, период измерения,
watchdog-таймаут и начальная калибровка HX711.

## Схема подключения

```text
                 5 В зарядное / USB
                        |
                 micro USB Lolin
                        |
       +----------------------------------+
       |        Lolin NodeMCU v3          |
       |                                  |
       |  3V3  ----+---------- HX711 VCC  |
       |           +---------- OLED VCC   |
       |  GND  ----+---------- HX711 GND  |
       |           +---------- OLED GND   |
       |                                  |
       |  D2 GPIO4  ------------ HX711 DT |
       |  D1 GPIO5  ------------ HX711 SCK|
       |  D6 GPIO12 ------------ OLED SDA |
       |  D7 GPIO13 ------------ OLED SCL |
       |                                  |
       |  D5 GPIO14 --------+             |
       |                    |             |
       +--------------------|-------------+
                            |
                       контакт 2
                    3-пин переключателя

       контакт 1 ---------------- 3V3     UseExistedWiFi
       контакт 3 ---------------- GND     StandAlone


       YZC-516C 1t                 HX711
       +----------+              +--------+
       | E+       |--------------| E+     |
       | E-       |--------------| E-     |
       | S+ / A+  |--------------| A+     |
       | S- / A-  |--------------| A-     |
       +----------+              +--------+

       OLED GM009605 v4.2 (SSD1306 128x64 I2C)
       +----------+
       | VCC      |---- 3V3
       | GND      |---- GND
       | SDA      |---- D6 (GPIO12)
       | SCL/SCK  |---- D7 (GPIO13)
       +----------+
```

Полная коммутация режима:

- `UseExistedWiFi`: общий контакт переключателя на `D5`, выбранный контакт на
  `3V3`. Иначе словами, для подключения к существующей WiFi-сети надо замкнуть
  `D5` на `3V3`.
- `StandAlone`: общий контакт переключателя на `D5`, выбранный контакт на
  `GND`. Иначе словами, для собственной точки доступа надо замкнуть `D5` на `GND`.

Цвета проводов тензодатчика у разных партий могут отличаться. Частый вариант:
красный `E+`, чёрный `E-`, зелёный `A+`, белый `A-`. Перед пайкой лучше
проверить маркировку или паспорт конкретного датчика.

HX711 и OLED питаются от `3V3`, чтобы цифровой выход `DT` и логика дисплея
не отдавали 5 В на вход ESP8266. Земля Lolin, HX711, OLED и переключателя
должна быть общей. OLED сидит на отдельных I2C-пинах `D6`/`D7`, потому что
`D1`/`D2` заняты HX711. На многих модулях GM009605 пин `SCK` = I2C `SCL`.
Адрес дисплея обычно `0x3C`. Пин `D8` не используется, потому что `GPIO15`
участвует в загрузке ESP8266.

На OLED:

- до первого измерения: `IP:порт` и версия прошивки в две строки;
- во время измерения: текущий вес крупными цифрами с одной десятичной;
- после измерения: чередование текущего максимума (крупнее) и прошлого
  максимума (мельче, с микро-меткой `L` справа внизу) раз в
  `displaySwapSec` секунд (заводское значение `3`).

## Что делает прошивка

После старта прошивка:

1. читает конфигурацию из EEPROM;
2. если EEPROM пустая, записывает заводские значения и WiFi-данные из сборки;
3. читает переключатель режима;
4. подключается к WiFi или поднимает свою точку доступа;
5. запускает HTTP-сервер на порту `80` и WebSocket на порту `81`;
6. читает HX711 без `delay` в основном цикле.

Вес считается так:

- текущий вес обновляется каждые `PERIOD_VESA_MS`;
- измерение начинается, когда вес стал не меньше `triggerKg`;
- максимум текущего измерения копится в `maxTekushiyKg`;
- когда истёк `periodSec` или вес упал ниже триггера дольше чем на
  `PAUZA_KONCA_IZMERENIYA_MS`, измерение завершается, а `maxTekushiyKg`
  сохраняется на экране/вебе; при старте следующего измерения прежний
  максимум уходит в `maxProshliyKg`.

## Веб-страница

Открой адрес контроллера в браузере:

- в режиме `UseExistedWiFi` адрес выводится в Serial Monitor;
- в режиме `StandAlone` подключись к сети `lolinsilomer`, пароль `lolinsilomer`, затем
  открой `http://192.168.4.1/`.

На странице есть:

- текущий вес в кг с одной цифрой после запятой;
- максимальный вес текущего измерения в кг;
- максимальный вес прошлого измерения в кг;
- настройка триггерного веса в кг;
- настройка периода измерения в секундах;
- настройка смены записей на OLED в секундах (`displaySwapSec`);
- настройка watchdog-таймаута в секундах;
- версия прошивки справа внизу (`fw N`);
- настройка логина и скрытого пароля новой WiFi-сети;
- настройка имени устройства для будущей веб-админки;
- сброс всех настроек в заводские;
- запрос перезагрузки через watchdog.

После нажатия кнопок на странице есть два признака, что действие принято:

- сама кнопка коротко "продавливается";
- внизу страницы обновляется нижний статус действия.

Сообщения в нижнем статусе:

- `Настройки сохранены.`;
- `Tare выполнен: текущий пустой датчик принят за 0 кг.`;
- `Калибровка выполнена.`;
- `Сброс выполнен: заводские настройки восстановлены.`;
- `Watchdog-перезагрузка запрошена.`;
- при ошибке там же пишется текст ошибки API.

## API

Все HTTP-запросы идут на порт `80`.

`GET /api/config` возвращает конфигурацию. Пароль WiFi маскируется:

```json
{
  "modelId": "silomer-stanovaya",
  "firmwareVersion": 1,
  "deviceName": "silomer-stanovaya",
  "wifiSsid": "MoyaWiFiSet",
  "wifiPass": "********",
  "triggerKg": 5.0,
  "periodSec": 10,
  "displaySwapSec": 3,
  "watchdogSec": 30,
  "calibrationScale": 4718.0,
  "calibrationOffset": 0,
  "sensorMaxKg": 1000.0
}
```

`modelId` - постоянный идентификатор модели устройства из `config.h`.
Его не путать с именем устройства: `deviceName` может быть
"силомер на 1 этаже", "силомер в подвале", а `modelId` остаётся
`silomer-stanovaya`, чтобы админка при сканировании сети понимала тип
устройства. На веб-странице `modelId` не показывается и через веб/API
не меняется.

`firmwareVersion` - константа `FIRMWARE_VERSION` из `config.h`. Её
наращивают на `+1` при каждой правке прошивки. Через API её нельзя
изменить, только прочитать.

`POST /api/config` принимает JSON с любыми из полей и обновляет их
одним телом:

```json
{
  "triggerKg": 20.0,
  "periodSec": 15,
  "displaySwapSec": 3,
  "watchdogSec": 30,
  "calibrationScale": 4718.0,
  "calibrationOffset": 0,
  "sensorMaxKg": 1000.0,
  "deviceName": "silomer-1",
  "wifiSsid": "NewWiFi",
  "wifiPass": "new-password"
}
```

Один параметр можно читать и менять отдельно:

- `GET /api/config/<ключ>` → например `{"displaySwapSec":3}`
- `PUT /api/config/<ключ>` с телом `{"value":3}`

Ключи: `triggerKg`, `periodSec`, `watchdogSec`, `displaySwapSec`,
`calibrationScale`, `calibrationOffset`, `sensorMaxKg`, `deviceName`,
`wifiSsid`, `wifiPass`. Только чтение: `modelId`, `firmwareVersion`.

`GET /api/status` возвращает статус:

```json
{
  "uptimeSec": 123,
  "modelId": "silomer-stanovaya",
  "firmwareVersion": 1,
  "deviceName": "silomer-stanovaya",
  "wifiMode": "UseExistedWiFi",
  "ip": "192.168.1.50",
  "tekushiyVesKg": 12.3,
  "maxTekushiyKg": 45.6,
  "maxProshliyKg": 44.1,
  "triggerKg": 5.0,
  "periodSec": 10,
  "displaySwapSec": 3,
  "izmerenieAktivno": true,
  "watchdogSec": 30,
  "watchdogStatus": "ok",
  "calibrationScale": 4718.0,
  "calibrationOffset": 0,
  "sensorMaxKg": 1000.0,
  "wsClients": 1,
  "hx711Ready": true,
  "oledReady": true,
  "freeHeap": 22000
}
```

Админка будущего сканера сети должна смотреть именно на `modelId` в
`/api/status`, а не на `deviceName`.

## Почему может зависать

ESP8266 "зависает" почти всегда не сам по себе, а потому что `loop()`
перестаёт крутиться или перестаёт вызывать `server.handleClient()`.

Главные причины в этой прошивке:

1. **Бесконечный `wait_ready()` библиотеки HX711.**  
   `read()`/`get_units()`/`tare()` внутри ждут DOUT=`LOW` без таймаута. Если
   датчик/провод DT отвалился, `loop()` застревает в ожидании и веб молчит.
   Soft WDT при этом может не сработать, потому что внутри есть `delay(0)`.
   Сейчас чтение веса, tare и calibrate сначала ждут через
   `wait_ready_timeout(... / 1200 мс)` и не зависают навсегда.

2. **Вложенный `server.handleClient()` из HTTP-обработчика.**  
   Раньше ожидание HX711 в `/api/tare` и `/api/calibrate` вызывало
   `handleClient()` повторно. На ESP8266 это ломает веб-сервер и выглядит как
   зависание. Сейчас ожидание HX711 не вызывает `handleClient`.

3. **Кнопка reboot.**  
   Раньше после таймаута watchdog стоял пустой `while(true)`. Это и есть
   намеренное зависание до аппаратного WDT. Сейчас после таймаута вызывается
   `ESP.restart()`.

4. **Долгий WiFi.connect при старте.**  
   До 20 секунд плата молчит по HTTP, пока ищет сеть. Это не зависание, но
   выглядит так сразу после перезапуска.

5. **Питание.**  
   Слабый USB/зарядник даёт brownout при WiFi TX: плата внезапно
   перезапускается или "отваливается". Это железо, не логика скетча.

6. **Мало `freeHeap`.**  
   Если куча заканчивается, поведение становится непредсказуемым. Смотри
   `freeHeap` в `/api/status`.

Как отличить:

- Serial продолжает печатать `ves=...` , а веб молчит → почти наверняка
  блокировка вне `handleClient` или перегруженный WiFi.
- Serial тоже молчит и нет Soft WDT/Exception → чаще питание или бесконечный
  wait без yield.
- В Serial есть `Soft WDT reset` / `Exception` → смотри стек; раньше так мог
  заканчиваться пустой `while(true)` после reboot.

`POST /api/reset` сбрасывает конфигурацию в заводскую.

`POST /api/reboot` запрашивает перезагрузку. После `watchdogSec` секунд
контроллер делает `ESP.restart()`. Раньше тут был пустой `while(true)` ради
аппаратного watchdog, и это выглядело как зависание устройства.

`GET /api/status` также отдаёт `freeHeap` — свободную кучу ESP8266. Если
число быстро падает к нескольким килобайтам, возможны странные зависания из-за
нехватки памяти.

`POST /api/tare` принимает текущую пустую платформу/крюк за `0 кг`, сохраняет
новый `calibrationOffset` в EEPROM и возвращает конфигурацию. Перед чтением
API ждёт готовность HX711 до `1200 мс`, потому что `is_ready()` может быть
ложным именно в момент HTTP-запроса: основной цикл уже забрал предыдущий
отсчёт, но новый ещё не готов.

`POST /api/calibrate` принимает эталонный вес в кг и пересчитывает
`calibrationScale`. Перед чтением эталона API тоже ждёт готовность HX711 до
`1200 мс`:

```json
{
  "knownKg": 3.0
}
```

Если сейчас 3 кг показываются как 33.7 кг, причина в старом коэффициенте:
`33.7 / 3.0 = 11.23`, поэтому `420 * 11.23 = 4718`. Это значение теперь
задано как заводское `ZAVOD_HX711_SCALE`, но его можно менять через API и
веб-страницу без правки исходников.

Последняя проверка на текущем стенде:

- до калибровки с гантелью 3 кг было около `2.84 кг`;
- `POST /api/calibrate` с `{"knownKg":3.0}` выполнился успешно;
- после калибровки стало около `3.01 кг`;
- сохранённый `calibrationScale` стал `4478.333`;
- `hx711Ready:false` в `/api/status` не всегда означает неисправность датчика:
  если вес продолжает обновляться, это только момент между отсчётами HX711.

`GET /swagger` отдаёт Swagger UI. Сама OpenAPI-схема лежит в
`/api/openapi.json`. Интерфейс Swagger грузит JS/CSS с CDN, поэтому в режиме
AP без интернета может открыться только JSON-схема.

WebSocket для онлайн-данных веса доступен как `ws://IP:81/api/ws`. Библиотека
`WebSocketsServer` на ESP8266 слушает отдельный порт, поэтому это не тот же
HTTP-порт `80`.

## Установка инструментов

Нужен `arduino-cli`, ядро ESP8266 и библиотеки:

```bash
arduino-cli config init
arduino-cli config add board_manager.additional_urls \
  https://arduino.esp8266.com/stable/package_esp8266com_index.json
arduino-cli core update-index
arduino-cli core install esp8266:esp8266

arduino-cli lib install "HX711 Arduino Library"
arduino-cli lib install "ArduinoJson"
arduino-cli lib install "WebSockets"
arduino-cli lib install "Adafruit SSD1306"
arduino-cli lib install "Adafruit GFX Library"
arduino-cli lib install "Adafruit BusIO"
```

Плата Lolin NodeMCU v3 собирается как `esp8266:esp8266:nodemcuv2`.

## Сборка и заливка

Один раз создай `.env`:

```bash
cd /home/blobby/work_dir/vibecode-arduino/silomer-stanovaya
cp .env.primer .env
nano .env
```

Пример важных переменных:

```bash
WIFI_SSID=MoyaWiFiSet
WIFI_PASS=moy-skrytyy-parol
PORT=COM4
REZHIM=wsl
```

Собрать:

```bash
./sborka.sh
```

Собрать и залить:

```bash
./sborka.sh zalit
```

Для обычного Linux поставь `REZHIM=linux` и порт вида `/dev/ttyUSB0`.

## Калибровка

В `config.h` сейчас стоит стартовое значение:

```cpp
const float ZAVOD_HX711_SCALE = 4718.0f;
const long ZAVOD_HX711_OFFSET = 0;
const float ZAVOD_SENSOR_MAX_KG = 1000.0f;
```

`sensorMaxKg` - номинальный максимум датчика. Для текущего YZC-516C 1t это
`1000 кг`. Если поставить другой датчик, например на `100 кг`, поменяй
`sensorMaxKg` через веб/API или заводское значение в `config.h`.

Как калибровать на реальном датчике:

1. включить без нагрузки;
2. нажать `Tare: принять пустой датчик за 0 кг`;
3. повесить известный груз;
4. в поле "Эталонный вес для калибровки, кг" указать реальный вес;
5. нажать "Откалибровать по текущему весу".

Если показания идут с обратным знаком, поменяй местами `A+` и `A-` на HX711
или сделай `calibrationScale` отрицательным.

Auto-tare при старте по умолчанию выключен. Это важно: если на датчике уже
висит гантеля, автоматический tare сделал бы этот вес новым нулём. Ноль лучше
задавать вручную кнопкой/API, когда датчик реально пустой.
